引言：异常路径才是真正的攻击面 ⚡

安全审计中，我们习惯性地关注「正常流程」——认证怎么做、授权怎么查、输入怎么校验。但今天的两个漏洞揭示了一个被系统性忽视的真相：

攻击者不走正门。他们专门找「出错时会发生什么」——解密失败时、密码重置时、token 无效时。异常路径没有被认真设计，只有被随意填充的 fallback。

第一个漏洞：密码学库在解密/解封装失败时静默降级到不安全模式，20+ CVE 同一模式。第二个漏洞：预认证的密码重置端点存在 SQLi，直接向会话表注入伪造 admin 会话。两者都是「异常路径」上的 Fail-Open 设计缺陷。

🔐 openssl_encrypt 20+ CVE — 密码学 Fail-Open 降级

背景

2026 年 8 月，NVD 集中披露了 openssl_encrypt（Python 密钥管理/PQC 库）的 20+ CVE（CVE-2026-74900/74901/74875/74894 等）。这不是 20 个不同的 bug——而是同一种设计错误在每个密码学操作中的重复出现。

核心模式

这个库的几乎每一条 except: 分支都在做同一件错事：把「操作失败」当成「切换到更弱模式」的触发器，而非「终止」。

# 模式1: KEM 解封装失败 → 仿真模式
try:
    shared_secret = kem.decapsulate(ciphertext)
except DecapsulationError:
    # ❌ Fail-Open: 回退到 16 字节确定性派生
    shared_secret = derive_simulation_key(16)

# 模式2: AES-GCM 解密失败 → 无认证 AES-CTR
try:
    plaintext = aes_gcm_decrypt(key, nonce, ciphertext, tag)
except InvalidTag:
    # ❌ Fail-Open: 丢弃认证，用 CTR 模式继续
    plaintext = aes_ctr_decrypt(key, nonce, ciphertext)

# 模式3: 可选依赖缺失 → 校验静默跳过
if jsonschema_available:
    validate(data, schema)
# ❌ jsonschema 没装 = 没校验，不是报错

# 模式4: Token 验证 → 接受任意非空 Bearer
def verify_api_token(token):
    if not token:
        raise AuthError
    # ❌ 只检查非空，不验证签名
    return True

为什么这是系统性问题

密码学代码唯一正确的失败处理是 raise 终止。但现实中，开发者面对 except 块时的直觉是「不能让程序崩溃」——于是他们加了 fallback，而 fallback 恰好绕过了安全保证。

更隐蔽的是「可选依赖→校验变 no-op」模式：if jsonschema_available: validate() 看起来优雅地处理了依赖缺失，但实际含义是「没装库 = 没校验 = 一切通过」。

审计方法

# 定位所有密码学异常/fallback 分支
grep -rn "except\|fallback\|simulation\|degraded\|downgrade" src/

# 检查可选依赖控制的安全逻辑
grep -rn "if.*available\|if.*installed\|try.*import" src/ | grep -i "valid\|check\|verify\|auth"

# 验证解密失败是否 raise
# 构造无效密文/tag → 观察是抛异常还是静默返回

迁移目标

  • PQC/后量子密码库：Kyber/ML-KEM 的 decapsulate 失败路径——这是新蓝海，实现质量远逊于经典密码
  • AEAD 用法：AES-GCM tag 验证失败后是否用明文继续
  • 协议协商降级：TLS→弱 cipher、SMB→NTLMv1
  • JWT/证书验证：verify 失败→继续处理（而非拒绝）

💉 Metabase SQLi→会话表注入 — 铸造管理员会话

背景

CVE-2026-72898（CVSS 10.0，CISA KEV 在野利用）：Metabase 的 /reset_password 端点存在预认证 SQL 注入，攻击者不仅能 dump 数据，还能直接向 core_session 表 INSERT 伪造的 admin session。

攻击链还原

# Step 1: 预认证端点——密码重置按设计不需要登录
POST /api/session/reset_password
Content-Type: application/json

{
  "token": "' UNION SELECT 'fake-session-id','admin',1,'2026-12-31'--",
  "password": "anything"
}

# Step 2: SQLi 写原语 → 向 core_session 表注入
# 注入的 SQL 被拼接为 INSERT，创建了一个 admin 的有效 session

# Step 3: 使用伪造 session 访问管理接口
GET /api/user/current
Cookie: Metabase.SESSION=fake-session-id
# → 返回 admin 用户信息，完全接管

为什么预认证端点是 SQLi 富矿

密码重置、注册、邮箱激活、token 验证——这些端点按设计就不需要认证，却必然要查数据库（验证 token、查找用户、检查邮箱）。它们比登录端点更少被安全团队关注，却是 SQLi 的天然高发区。

SQLi 写原语 = 最短路提权

当 session/API key 存储在数据库中时，一个可写的 SQLi（INSERT/UPDATE）就是铸造任意用户会话的能力。不需要暴力破解密码、不需要 OS 权限提升——直接在 DB 层面成为 admin。

🔑 规则：session 存 DB 时，可写 SQLi = 铸造任意用户会话 = 最短路提权。

🧠 共性方法论：失败路径枚举法

两个漏洞的深层共性是「异常路径未经安全设计」。这催生了一个可复用的审计方法论：

1. 失败路径枚举

对系统中每个安全关键操作，列出所有可能的失败场景，确认每个失败路径是 fail-closed（拒绝/终止）还是 fail-open（降级/跳过/返回成功）：

# 失败路径枚举清单
┌─────────────────────────┬──────────────────────────┬──────────┐
│ 操作                     │ 失败场景                  │ 应该是    │
├─────────────────────────┼──────────────────────────┼──────────┤
│ KEM decapsulate         │ 密文无效                  │ raise ❌  │
│ AES-GCM decrypt         │ tag 不匹配               │ raise ❌  │
│ JSON Schema validate    │ 依赖未安装               │ raise ❌  │
│ Token verify            │ 签名无效                  │ reject ❌ │
│ 密码重置 token 验证      │ token 不存在/过期         │ reject ❌ │
│ 会话查找                │ session_id 不存在          │ reject ❌ │
└─────────────────────────┴──────────────────────────┴──────────┘

# 任何「降级」「跳过」「返回成功」= 漏洞

2. 预认证攻击面枚举

系统化地枚举所有不需要认证的端点，按「是否查 DB」分类，优先测试查 DB 的端点：

# 预认证端点分类
├── 不查 DB（低风险）
│   ├── /health, /version, /metrics
│   └── 静态资源
├── 查 DB 且只读（中风险 — SQLi 目标）
│   ├── /reset_password, /verify_email
│   └── /api/token/verify, /api/setup/check
└── 查 DB 且可写（高风险 — SQLi + 写原语）
    ├── /register, /activate
    └── 任何 UPDATE/INSERT 路径

🎯 实战建议

立即可做

  1. 审计任意 PQC/密钥管理库的失败路径：grep -rn "except\|fallback\|simulation" 定位所有异常分支，验证 decrypt/decapsulate 失败时是否 raise
  2. 对 SRC 目标建立「预认证端点清单」：枚举所有无需登录的端点，逐一测单引号/时间盲注，重点找 session 表名以评估「写会话」可行性

长期积累

  • 建立「能力等价 API 清单」：对每个危险能力（文件读/写、命令执行、反射、序列化）枚举语言生态内的全部等价入口
  • 建立「失败路径枚举」习惯：每次审计新系统时，先扫一遍 except/fallback/downgrade 分支
